# grpx

一个小而完整的 GRPO 训练框架：单轮任务和多轮智能体任务共用一套代码，GRPO、Dr. GRPO、GiGPO 通过一个配置项切换，单机单卡即可运行。

项目处于早期阶段。目前只在 Qwen2.5-0.5B 和 Qwen2.5-1.5B 上验证过，任务是几个示例任务和 GSM8K，接口可能调整。

## 特点

- **你只需要写任务本身**：单轮任务写一个回报函数，多轮任务写一个环境类，其余（采样、分组、优势计算、训练、评测、保存）都有默认实现。
- **单轮和多轮是同一条路径**：单轮任务就是只有一步的环境，轨迹格式、训练代码、评测代码完全相同。
- **算法用预设名切换**：`grpo`、`dr_grpo`、`gigpo`，需要时再逐项覆盖。
- **训练前先预检**：`grpx doctor` 在正式训练前检查任务、回报函数、学习率和显存，把常见问题提前指出来。
- **采样与训练严格一致**：采样不继承模型自带的生成配置，采样温度随轨迹记录并在训练端还原，旧策略概率由训练端自己计算。
- **默认不依赖推理服务**：本地后端下采样和训练共用同一个模型对象，Windows 和 Linux 都能直接运行。需要更快的采样时，可以换成 vLLM 后端。

## 安装

需要 Python 3.11 及以上和一张支持 CUDA 的显卡。

**第一步：安装 GPU 版 PyTorch。** 请按 [PyTorch 官网](https://pytorch.org/get-started/locally/)给出的命令安装和你的 CUDA 版本对应的包，然后确认它能用到显卡：

```bash
python -c "import torch; print(torch.__version__, torch.cuda.is_available())"
```

输出的最后一项应该是 `True`。如果跳过这一步直接安装 grpx，有的环境下 pip 会装上不带 CUDA 的版本，预检会在检查 CUDA 时报错。

**第二步：在项目根目录下安装 grpx。**

```bash
pip install -e .
```

其余依赖（`transformers>=4.56`、`peft` 等）会自动装上。

**模型下载。** 示例使用 Hugging Face 上的 `Qwen/Qwen2.5-0.5B-Instruct`，第一次运行时会自动下载，约 1 GB。访问 Hugging Face 不稳定时，可以通过环境变量 `HF_ENDPOINT` 指定镜像站点的地址。

**所有命令都要在项目根目录下执行。** 配置里的 `examples.arithmetic:reward_function` 这类写法是从当前目录开始查找模块的，换到别的目录运行会找不到 `examples` 模块。任务代码放在别处时，把它所在的目录加入 `PYTHONPATH`。

## 快速开始

先用最简单的任务确认环境没问题。四位数加法是单轮任务，0.5B 的模型，几分钟跑完：

```bash
# 1. 预检：几十秒内告诉你这份配置能不能训
grpx doctor --config configs/arithmetic.toml

# 2. 训练
grpx train --config configs/arithmetic.toml
```

训练过程中每隔几轮会打印一次评测成功率，它应该从 0.65 左右升到 0.8 以上。

多轮任务换一份配置即可，命令相同：

```bash
grpx doctor --config configs/guess_number.toml
grpx train --config configs/guess_number.toml
```

临时修改参数不需要改文件：

```bash
grpx train --config configs/guess_number.toml \
    --set training.algorithm=grpo \
    --set training.learning_rate=2e-5 \
    --set training.seed=1
```

训练产物保存在 `outputs/<运行名>/` 下，运行名默认是启动时的时间戳：

| 文件 | 内容 |
|---|---|
| `resolved_configuration.json` | 本次运行的完整配置（模型、后端、任务、训练），已合并 `--set` 的覆盖项 |
| `config.json` | 训练参数 |
| `metrics.jsonl` | 每轮一条记录 |
| `checkpoint-<轮次>/` | LoRA 权重，以及恢复训练所需的状态 `training_state.pt`（优化器、调度器、随机状态） |

### 恢复训练

训练中断后，从最近一个检查点接着跑：

```bash
grpx train --resume outputs/<运行名>
```

延长一次已经跑完的训练：

```bash
grpx train --resume outputs/<运行名> --set training.iterations=40
```

- 配置从运行目录里读取，不需要再传 `--config`。
- 恢复时只能修改 `iterations`、`evaluation_interval`、`checkpoint_interval`、`shift_measurement_interval`，以及只影响显存的 `max_rows_per_minibatch`、`max_tokens_per_minibatch`、`memory_fraction`。要换其他配置，请开始一次新的运行。
- 检查点之后写入的日志会被丢弃并重新生成，`metrics.jsonl` 里的轮次保持连续。
- `checkpoint-0010` 表示已完成 10 轮。检查点是写完整之后才生效的，保存到一半被中断不会留下损坏的检查点。

自带两个示例：

| 配置 | 类型 | 任务 |
|---|---|---|
| `configs/arithmetic.toml` | 单轮 | 四位数加法 |
| `configs/guess_number.toml` | 多轮 | 猜数字，每次猜测后环境反馈大了或小了 |

另外两个任务需要 vLLM 后端：`configs/gsm8k_vllm.toml`（GSM8K）和 `configs/frozen_lake_vllm.toml`（冰湖寻路，多轮）。

## 写自己的任务

### 单轮任务

需要三样东西：一个数据集函数、一个回报函数、一份配置。

`my_task.py`

```python
import random


def make_dataset(size, seed=0):
    random_generator = random.Random(seed)
    dataset = []
    for _ in range(size):
        word = "".join(random_generator.choice("ab") for _ in range(8))
        dataset.append({
            "prompt": f"字符串 {word} 里有几个 a？只输出数字。",
            "answer": word.count("a"),
        })
    return dataset


def reward_function(prompt, completion, sample):
    digits = "".join(character for character in completion if character.isdigit())
    if not digits:
        return 0.0
    difference = abs(int(digits) - sample["answer"])
    if difference == 0:
        return 1.0
    return max(0.0, 0.5 - 0.1 * difference)      # 没答对也按接近程度给部分分


def success_function(completion, sample):
    digits = "".join(character for character in completion if character.isdigit())
    return bool(digits) and int(digits) == sample["answer"]
```

`my_task.toml`

```toml
[model]
name = "Qwen/Qwen2.5-0.5B-Instruct"

[task]
reward_function = "my_task:reward_function"
success_function = "my_task:success_function"
dataset = "my_task:make_dataset"
train_dataset_options = { size = 2000, seed = 0 }
evaluation_dataset_options = { size = 200, seed = 1 }

[training]
algorithm = "grpo"
```

约定：

- 数据集函数返回一个列表，每个元素是一道题的字典。单轮任务的字典里必须有 `prompt`，其余字段随意，会原样传给回报函数。
- 回报函数接收三个参数 `(prompt, completion, sample)`，返回一个有限的 `float`。numpy 数值请用 `float(...)` 转换。
- 成功判定接收两个参数 `(completion, sample)`，返回布尔值。它是可选的：提供后日志里会有成功率，不提供则只看回报。
- 被生成长度截断的回答由框架统一处理：不算成功，回报按 `training.truncated_reward` 计（默认 0），不管回报函数对它的文本给出什么结果。回报函数只能看到文本，无从知道回答是否写完，所以这一条不需要、也不应该在回报函数里自己判断。

### 多轮任务

写一个环境类，实现下面的方法：

```python
class MyEnvironment:
    def reset(self, sample, seed):
        """开始一局。返回初始消息列表。"""
        self.target = sample["target"]
        self.successful = False
        return [{"role": "user", "content": "……任务说明……"}]

    def step(self, action_text):
        """处理模型的一次回答。返回（新增的消息列表, 这一步的奖励, 是否结束）。"""
        if self._is_correct(action_text):
            self.successful = True
            return [], 1.0, True
        return [{"role": "user", "content": "……环境的反馈……"}], 0.0, False

    def state_key(self):
        """可选。返回标识当前环境状态的字符串，供 GiGPO 按状态分组；没有状态概念时返回 ""。"""
        return ""

    def is_successful(self):
        """可选。返回这一局是否成功。"""
        return self.successful

    def metrics(self):
        """可选。返回这一局的任务自定义指标，键是名字，值是有限的数值。"""
        return {"my_metric": 0.0}
```

`metrics()` 返回的每一项会在所有轨迹上取平均，以 `environment_<名字>` 写入训练日志，以 `evaluation_environment_<名字>` 写入评测记录。成功率和回报只反映结果，用它可以记录过程，比如"有多大比例的步骤是有效操作"。

配置里把 `reward_function` 换成 `environment`，并设置步数上限：

```toml
[task]
environment = "my_task:MyEnvironment"
environment_options = {}
dataset = "my_task:make_dataset"
train_dataset_options = { size = 2000, seed = 0 }
evaluation_dataset_options = { size = 200, seed = 1 }

[training]
algorithm = "gigpo"
max_steps = 6
```

约定：

- 每条轨迹使用一个独立的环境实例，环境可以放心地保存状态。
- `step` 必须能处理任意文本，包括空字符串和完全不符合格式的回答。
- 同一组内的轨迹以相同的 `sample` 和 `seed` 调用 `reset`，应当从相同的初始状态出发。
- 模型的某次回答被生成长度截断时，这一局立即结束，并且不算成功。被截断那一步的回报按 `training.truncated_reward` 计（默认 0），之前各步已经拿到的回报保留。

完整示例见 `examples/guess_number.py`。

### 设计回报函数的建议

GRPO 只能从组内差异中学习：一组里所有回答得分相同，这一组就不产生梯度。

- **尽量给分级回报，而不是只有对和错。** 只有 0 和 1 时，全错的组和全对的组都没有信号。按接近程度、完成进度给部分分，全错的组里也有好坏之分。
- **答错的得分要严格低于答对。** 否则模型可以靠"接近"拿到和答对一样的分数。
- **成功与否单独判定，不要用"回报等于 1"代替。** 这正是 `success_function` 和 `is_successful` 存在的原因。
- **起点不能太低。** 初始成功率接近 0 且没有部分分时，模型没有可学的东西。先改进提示词或降低难度。
- **组内只看相对高低，微小的差别也会被放大。** 默认的预设把组内回报除以标准差，所以一组里 -0.48 和 -0.50 的差别，与 1 和 0 的差别产生的梯度一样强。设计回报时，先把几种典型结局的得分按高低排好，确认这个顺序就是你想要的：两种结局你不想让模型偏向任何一个，就给它们完全相同的分数。
- **惩罚要和模型当前的水平相称。** 给某种失败加惩罚之前，先算一下"什么都不做"能得多少分。我们在冰湖寻路上给掉洞加过惩罚，结果模型学会的是输出无效回答、原地不动，因为它离"绕开洞"还很远，而"不动"立刻就能避开惩罚。用几个手写的简单策略（不动、乱走、朝目标直走）跑一遍环境，比较它们的平均得分，可以在训练之前发现这类问题。
- **回报可以为负时，重新设置 `truncated_reward`。** 被截断的那一步默认按 0 分计。回报全部非负时，这是最差的结果；一旦正常的一步可以得负分，被截断反而可能比正常结束得分更高，模型会学着把回答写到截断。这时把 `truncated_reward` 调低，直到被截断的一局不比最差的正常结局得分高。预检会检查这一点，并报告截断比多大比例的正常结局得分更高。
- **检查有没有"多写也能得分"的路径。** 只从回答里提取答案、不管答案之后还有什么的回报函数，会奖励"给出答案后继续写"。模型会利用这一点，表现为回答越来越长、截断率上升。训练中截断率突然升高时，先抽几条被截断的回答看原文。

## 配置说明

### `[model]`

| 字段 | 默认值 | 说明 |
|---|---|---|
| `name` | 必填 | 模型名称或本地路径 |
| `lora_rank` | 16 | LoRA 的秩 |
| `lora_alpha` | 32 | LoRA 的缩放系数 |
| `lora_target_modules` | `"all-linear"` | 注入 LoRA 的层，原样传给 PEFT。可以写成模块名的列表，比如 `["q_proj", "k_proj", "v_proj", "o_proj"]`。MoE 模型请显式指定，见"训练 MoE 模型" |
| `dtype` | `"float32"` | 训练端的精度。`"bfloat16"` 启用混合精度，见"训练端的速度和显存"一节 |

### `[backend]`

| 字段 | 默认值 | 说明 |
|---|---|---|
| `type` | `"huggingface"` | 采样后端：`"huggingface"`（本地）或 `"vllm"` |
| `max_new_tokens` | 32 | 每次回答的生成上限 |
| `temperature` | 1.0 | 采样温度 |
| `stop_strings` | `[]` | 停止串。生成到其中任何一个就停下，停止串本身保留在回答里。用于工具调用，见"工具调用任务"一节 |
| `max_rows_per_batch` | 64 | 仅本地后端。采样时每批最多多少条 |
| `max_tokens_per_batch` | 32768 | 仅本地后端。采样时每批的 token 预算 |
| `base_url` | `"http://localhost:8000"` | 仅 vLLM 后端。推理服务的地址。可以写成列表，同时使用多个推理服务，见"使用多张显卡" |
| `max_concurrent_requests` | 64 | 仅 vLLM 后端。同时发出的请求数 |
| `adapter_path_local_prefix`、`adapter_path_server_prefix` | 无 | 仅 vLLM 后端。训练端和服务端看到的路径不同时，用这一对前缀做映射 |
| `server_model_name` | 无 | 仅 vLLM 后端。推理服务上基座模型的名字。服务用别名或本地路径加载模型、名字和 `[model].name` 对不上时填写 |

只对某一种后端有效的字段，写在另一种后端的配置里会直接报错。vLLM 后端的用法见"使用 vLLM 后端"一节。

### `[task]`

| 字段 | 说明 |
|---|---|
| `dataset` | 数据集函数，写成 `模块路径:函数名` |
| `train_dataset_options` | 传给数据集函数的参数，用于训练集 |
| `evaluation_dataset_options` | 同上，用于评测集；不填则不做评测 |
| `reward_function` | 单轮任务的回报函数 |
| `success_function` | 单轮任务的成功判定，可选 |
| `environment` | 多轮任务的环境类 |
| `environment_options` | 传给环境类构造函数的参数 |

`reward_function` 和 `environment` 二选一。

### `[training]`

| 字段 | 默认值 | 说明 |
|---|---|---|
| `algorithm` | `"grpo"` | 算法预设，见下一节 |
| `iterations` | 20 | 训练轮数 |
| `groups_per_iteration` | 16 | 每轮抽多少道题 |
| `group_size` | 8 | 每道题采样多少条回答，至少为 2 |
| `max_steps` | 6 | 每条轨迹的步数上限。单轮任务在第一步就结束，不受它影响 |
| `learning_rate` | 1e-5 | 学习率 |
| `warmup_iterations` | 5 | 线性预热的轮数 |
| `learning_rate_schedule` | `"constant"` | 预热之后学习率怎么变。`"constant"` 保持不变；`"cosine"` 按余弦逐渐降低，在最后一轮降到 `final_learning_rate_fraction` |
| `final_learning_rate_fraction` | 0.1 | 余弦衰减的终点，相对设定学习率的比例 |
| `updates_per_iteration` | 1 | 每轮数据上更新几次 |
| `max_approximate_kl` | 不限 | 多次更新时，偏离旧策略超过该值就提前停止 |
| `clip_range` | 0.2 | ratio 的裁剪范围 |
| `max_gradient_norm` | 1.0 | 梯度裁剪 |
| `row_weighting` | `"per_step"` | 多轮任务里各步等权，或按轨迹等权（`"per_trajectory"`） |
| `max_rows_per_minibatch` | 8 | 训练时每小批最多多少行。多轮任务里一步算一行，合并对话后仍按步数计 |
| `max_tokens_per_minibatch` | 4096 | 训练时每小批的 token 预算，即行数乘以补齐后的长度。单独一行就超过这个预算的，不参与更新 |
| `output_logit_chunk_size` | 512 | 输出层按多少个回答位置一块来计算，用来降低长回答任务的显存。设为 0 则一次算完。不影响训练结果 |
| `merge_append_only_turns` | `false` | 多轮任务里，把一条对话的各步合并成一次前向，见"训练端的速度和显存"一节 |
| `truncated_reward` | 0 | 回答被生成长度截断时，这一步的回报。多轮任务里只覆盖被截断的那一步，之前各步的回报保留。设为 `null` 则不覆盖，沿用回报函数或环境给出的值，不建议 |
| `evaluation_interval` | 10 | 每隔多少轮评测一次 |
| `shift_measurement_interval` | 1 | 每隔多少轮测一次步长指标；0 表示不测。测量要多做一次前向，调大可以缩短更新阶段的耗时，不影响训练结果 |
| `checkpoint_interval` | 10 | 每隔多少轮保存一次 |
| `device` | `"cuda"` | 训练端使用的设备，比如 `"cuda:1"` |
| `memory_fraction` | 0.6 | 训练端最多使用所在显卡的多大比例。和推理服务共用一张卡时保持默认；独占一张卡时可以设到 0.95 |
| `seed` | 0 | 随机种子 |
| `output_root` | `"outputs"` | 运行目录的上级目录 |
| `run_name` | 时间戳 | 运行目录的名字 |

小批之间做梯度累积，所以两个小批参数只影响显存占用，不影响训练结果。显存不足时调小它们。MoE 模型在 bfloat16 下有一个例外：换一种分批方式，个别 token 的数值会有可见的差别，但训练结果在我们的实验里没有受影响，见"训练 MoE 模型"。

字段名写错时，会直接提示最接近的正确写法。

### 训练端的速度和显存

默认配置偏保守：float32、每步单独前向、小批很小。下面三项可以单独开，也可以一起开，都不改变训练的结果。

**混合精度：`model.dtype = "bfloat16"`**

基座模型以 bfloat16 加载和前向，LoRA 参数、输出层和损失仍用 float32。主要收益是显存：我们在 1.5B 模型上看到训练端的显存峰值降了约三分之一，准确率没有可分辨的变化。单独打开它，速度提升有限；省下的显存要换成更大的小批才能变成速度。代价是 `shift_` 指标不再可靠，见"步长指标"一节。

采样后端是 vLLM 时，推理服务本来就是半精度，训练端也用 bfloat16 会让两边更一致。

**合并对话：`training.merge_append_only_turns = true`**

多轮任务里，默认每一步都把到这一步为止的完整对话前向一次。如果对话是只追加的，也就是每一步的提示都等于上一步的提示加上一步的回答再加新的消息，那么整条对话前向一次就能得到所有步的结果。打开这一项后，框架逐条检查轨迹，满足条件的合并，不满足的仍按原来的方式处理。日志里的 `merged_trajectory_fraction` 是被合并的轨迹占比。

合并前后的对数概率、损失和梯度在数值误差范围内相同。收益同样主要是显存，在猜数字上约减半。环境会改写或截断历史消息时，轨迹不满足只追加的条件，这一项不起作用。

**加大小批：`training.max_rows_per_minibatch`**

模型小、回答短的时候，更新阶段的时间主要花在小批的数量上，而不是 token 的数量上。显存有余量时把小批调大，更新会明显变快。在猜数字上，三项一起打开、小批从 8 行调到 32 行后，更新阶段的耗时降到原来的三分之一以下。

调大之前先跑一次预检，看"最坏小批"一项报告的显存峰值。使用 vLLM 后端、两个进程共用一张显卡时，不要让训练端贴近自己的显存上限，否则会拖慢推理服务。

## 三个算法预设

| 预设 | 组内除以标准差 | 长度归一 | 步级优势 |
|---|---|---|---|
| `grpo` | 是 | 按各自序列长度 | 无 |
| `dr_grpo` | 否 | 按固定常数 | 无 |
| `gigpo` | 是 | 按各自序列长度 | 有（权重 1.0，折扣 0.95） |

- **GRPO**：整条轨迹的回报减去组内均值、除以组内标准差，作为这条轨迹上每一步的优势。
- **Dr. GRPO**：去掉标准差归一和按序列长度的归一，用来消除原版对回答长度的偏置。适合回答长度差异大的任务。
- **GiGPO**：在轨迹级优势之外，把同组内处于相同环境状态的各步归在一起，比较它们之后的折扣回报，得到步级优势。适合多轮任务，需要环境提供 `state_key`。

选了 `gigpo` 而环境没有可用的状态键时，结果与 `grpo` 相同，预检会给出提示。

预设里的每一项都可以单独覆盖，对应的字段是 `normalize_std`、`length_normalization`、`step_advantage_weight`、`discount`。

### 怎么选：两次对比实验的结论

我们在两类任务上比较过这几个配置。多轮任务有两个。一个是猜数字的两个版本（Qwen2.5-0.5B）：一个版本每次反馈都告诉模型当前的可行区间，另一个版本不告诉，模型只能从对话历史推断。另一个是冰湖寻路（`examples/frozen_lake.py`）：在方格地图上绕开洞走到终点，最多 12 步，同一道题的各条轨迹会反复经过相同的位置，是专门为检验步级优势准备的，在 0.5B 和 1.5B 上都跑过。单轮任务是 GSM8K（Qwen2.5-1.5B），只比较了 GRPO 和 Dr. GRPO，因为单轮任务上 GiGPO 与 GRPO 没有区别。每个配置运行三个随机种子，在固定的评测集上用贪心解码评测。

**GiGPO：有时前中期学得更快，最终水平没有更高。**
猜数字的两个版本里都是同一个形态：训练中段 GiGPO 明显领先，到后期 GRPO 追平，终点的差别在种子间的波动范围之内。

冰湖寻路是按 GiGPO 的长处设计的：走进洞是某个位置上一个具体动作的后果，同组的轨迹又会反复经过同一个位置。结果仍然没有看到优势。

- 0.5B 上，两种算法都学不会利用"旁边是洞"这条信息，停在一个简单避洞规则的水平之下。GiGPO 更早学会不撞湖岸，最终成功率没有更高。
- 1.5B 上，两种算法都学会了避洞，达到那个简单规则的水平。三个种子的最终成功率范围互相重叠，训练中到过的最高成功率也相同。GiGPO 有两个种子在训练末段的评测结果起伏更大，其中一个在到达高点之后明显回落；只有三个种子，这一点只能算作迹象。

在我们试过的所有设定里，GiGPO 的终点都没有超过 GRPO。训练预算有限、任务和猜数字类似时，它可能更早给出可用的策略；除此之外没有理由优先选它。

提出 GiGPO 的论文报告的优势出现在步数长得多的任务上（一局最多 50 步）和更大的训练规模上，我们没有复现那个设定，上面的结论不能推广到那里。

**Dr. GRPO：没有观察到优势。**
它修正的是原版对回答长度的偏置。在回答只有两三个 token 的猜数字上，它学得更慢。在回答有几百个 token 的 GSM8K 上（Qwen2.5-1.5B），它和 GRPO 的准确率相同，最终的回答长度也没有可分辨的差别；答错的回答比答对的长约三成，这个比例在基座模型、GRPO、Dr. GRPO 三者上都一样，没有看到原版让错误回答越写越长的迹象。需要注意的是，Dr. GRPO 对回报函数的漏洞更敏感。它让一条回答在梯度里的分量正比于回答的长度，所以任何"写得长也能得分"的情况都会被放大。我们遇到过一次：早期的规则允许被截断的回答算作答对，模型学会了给出答案后不停笔、反复重复最后一句直到写满上限。GRPO 下这个倾向很弱，Dr. GRPO 下则表现为训练后期截断率突然升到两成以上。把规则改成"被截断的回答不算成功"之后，这个现象消退了。

**按轨迹等权：没有可测量的差别。**
多轮任务里，默认的按步等权会让步数多的轨迹在梯度里占比更高。改成按轨迹等权确实消除了这个偏置，但没有带来收益。

**切换预设时不需要重新调学习率。**
几个配置的优势数值尺度相差很大，但使用 AdamW 时，更新的幅度对 loss 的整体缩放基本不敏感。实测各配置的 `shift_` 指标在同一水平。不要按优势的尺度去换算学习率。

**这些结论的适用范围很窄。**

- 只在两个小模型（0.5B 和 1.5B）和三个任务上测过，每个配置三个种子。成功率相差几个百分点的，无法区分。
- 回答长度在不同种子之间的波动很大。只看一次运行，很容易把偶然的变长或变短当成算法的效果。
- 训练中途的领先可能在后期消失。只看某一轮的数值会得出相反的结论，比较时请看整条评测曲线。
- 模型大小会改变任务的性质。冰湖寻路上，0.5B 的瓶颈是读不懂观察，换哪种算法都一样；换成 1.5B 之后才轮到算法之间的比较。比较算法之前，先确认模型有能力完成任务。
- 步级优势依赖环境的 `state_key`。它在多大比例的步上生效，由 `step_signal_coverage` 给出；这个比例很低时，GiGPO 与 GRPO 没有区别。

换一个任务或模型，建议用自己的数据重新比较，而不是直接套用上面的结论。

## 在 GSM8K 上的结果

用 GSM8K 检验过框架在真实基准上是否有效。

| 设置 | |
|---|---|
| 模型 | Qwen2.5-1.5B-Instruct，LoRA 秩 16 |
| 训练 | GSM8K 训练集，60 轮，每轮 32 道题 × 8 条回答，学习率 5e-5 |
| 采样 | vLLM 后端，回答上限 768 个 token |
| 评测 | 完整测试集 1319 题，贪心解码，被截断的回答不算对 |
| 硬件 | 单张 RTX 4090，推理服务和训练端共用 |

| | 测试集准确率 |
|---|---|
| 训练前 | 0.676 |
| 训练后 | 约 0.76（六次运行在 0.744 到 0.778 之间） |

六次运行是 GRPO 和 Dr. GRPO 各三个随机种子，两种算法的结果没有可分辨的差别。一次训练在单卡上约半小时。

几点说明：

- 训练只用到了训练集里的一小部分题目，提升完整地迁移到了测试集上。
- 同一份权重重复评测，准确率有约 1 个百分点的抖动，来自推理服务的批处理。比这更小的差别没有意义。
- 回报函数只看最终答案是否正确，没有用到参考解答的中间步骤。

复现：

```bash
grpx doctor --config configs/gsm8k_vllm.toml
grpx train --config configs/gsm8k_vllm.toml
```

推理服务的启动方式见下一节，模型换成 `Qwen/Qwen2.5-1.5B-Instruct`，`--gpu-memory-utilization` 用 0.25，`--max-model-len` 用 4096。任务代码在 `examples/gsm8k.py`。

## 和 TRL 的对照

为了检验实现是否正确，我们用 TRL 的 `GRPOTrainer` 在 GSM8K 上做了一组设置对齐的训练。

**怎么对齐的**

- 模型、LoRA 设置、训练量相同：Qwen2.5-1.5B，每次更新 32 道题 × 8 条回答，更新 60 次，学习率 5e-5。
- 提示词和回报函数是同一份代码（`examples/gsm8k.py`），TRL 一侧的脚本直接导入它们。
- 评测用同一个脚本：两边训练出的 LoRA 权重都在完整测试集（1319 题）上贪心解码评测。
- TRL 一侧的脚本在 `scripts/compare_trl_gsm8k.py`，使用 TRL 1.18，`loss_type="grpo"`，vLLM 采样（colocate 模式）。

**结果**

| | TRL 1.18 | grpx |
|---|---|---|
| 测试集准确率 | 0.759–0.780（三个种子） | 0.744–0.778（六次运行），对照当天重跑一次为 0.763 |
| 每次更新的耗时 | 53–68 秒，平均约 60 秒 | 约 25 秒（一次运行） |
| 整张显卡的显存峰值 | 18.8–20.2 GB | 22.9 GB |

- **准确率一致。** 两个互相独立的实现，在相同的设置下得到范围重叠的结果。
- **这次对照里 grpx 每次更新快一倍多，占用的显存更多。** grpx 这次运行用的是偏向速度的设置：bfloat16，小批预算 2048 个 token、最多 8 行，输出层按 512 个位置分块，步长指标每 10 轮测一次，同卡的推理服务按 `--gpu-memory-utilization 0.35` 启动。调小小批预算或推理服务的显存比例可以少占显存，但会变慢。
- **单卡上能用的采样方式不同。** 这个规模下，TRL 不用 vLLM 时一次更新二十分钟没有跑完，并占满了 24 GB 显存；它的独立推理服务模式要求推理和训练在不同的显卡上，所以单卡只能用 colocate 模式。grpx 的本地后端和同卡的独立推理服务都可以用。

**读这组数字时要知道的**

- 耗时和显存各自只代表一种设置。两边都没有为这次对照专门调优，TRL 一侧尤其如此，批大小等参数是直接定的，没有尝试别的取值。不应据此得出谁更快的一般结论。
- 每次更新的耗时随回答长度变化。TRL 三次运行里最慢的那次，模型的回答全程更长（平均约 276 个 token，另外两次是 227 和 244），被截断的也更多。回答变长的漂移我们在 grpx 上同样见过，它和用哪个框架无关。grpx 一侧只有一次运行，没有测它在种子之间的波动。
- 两边用的 vLLM 版本不同（TRL 一侧 0.33，grpx 一侧 0.18），采样速度的差别里有这个因素。
- 有三处没有对齐，都是两个框架各自的设计，我们没有去统一：
  - 被截断的回答：grpx 记 0 分并参与训练，TRL 排除在损失之外。这类回答只占约百分之一，对准确率的影响应当很小。
  - 旧策略概率：grpx 每轮单独计算一遍，TRL 在每批数据只用一次时不单独计算。两种做法的梯度相同，grpx 多一次前向的耗时。
  - 混合精度：grpx 只把基座放在 bfloat16，LoRA、输出层和损失保留 float32，这会多占一些显存。

grpx 的目的不是比 TRL 准确率更高。它和 TRL 的差别在于：单轮和多轮任务共用一条路径、训练前的预检、训推一致的自动检查、工具调用所需的停止串，以及内置的 Dr. GRPO 和 GiGPO。只需要单轮任务上的 GRPO 时，TRL 是更成熟的选择。

## 工具调用任务

工具调用就是一种多轮任务：模型在回答里写出调用，环境执行后把结果作为下一条消息返回。`examples/gsm8k_calculator.py` 是一个完整的例子，模型可以用 `<calc>表达式</calc>` 调用计算器。

### 一定要配停止串

```toml
[backend]
stop_strings = ["</calc>"]
```

没有停止串时，模型写完调用不会停下来，而是自己编一个结果接着往下写。我们测到未训练的模型有四分之一以上的回答是这样的，这些回答比老实等结果的回答准确率低十个百分点以上，而且训练数据里会混进大量"在编造的工具输出上继续推理"的样本。配上停止串之后，生成到调用结束就停，这种情况从机制上消失。

被停止串截住的一步没有结束 token，训练时这一步就算到停止串为止。采样、评测和训练必须使用同一组停止串，它记录在运行目录的配置里。日志和预检会报告每一步是以结束 token、停止串还是长度上限结束的；只有长度上限算截断。

### 写这类环境时踩过的坑

- **提示里的示范会带偏未训练的模型。** 示范对话里每一轮都很短，模型就照着跳过推理直接作答。示范里要把推理写出来。
- **不用工具时，任务应该退化成对应的单轮任务。** 这样未训练时的成绩和单轮版接近，训练后的差别才能归因于工具。
- **答案行里的调用要按调用处理。** 模型常写出"答案标记后面跟一次调用"，如果把它当成最终答案，取到的是表达式里的数字。
- **无效的一轮如果没有任何代价，模型会利用它。** 我们见过模型学会第一轮故意不作答，等环境提醒后再答，白得一次补答机会。示例环境的 `invalid_turn_cost` 选项可以给它一点代价。
- **代价从最终回报里扣，不要给负分。** 示例环境的 `call_cost`（每次调用）和 `invalid_turn_cost`（每个无效轮）都只在答对时从最终回报里扣除，并且不低于 0。给中间步骤负分会让一局的总回报变成负数，这时被截断反而成了更好的结局；对答错的回答也扣分，则会在全组都答错时把模型推离调用工具。两项默认都是 0。
- **要限制一局的总长度。** 个别特别长的对话在训练时会占用过多显存。

### 我们观察到的结果

都是 Qwen2.5-1.5B，只用"最终答案是否正确"作为回报，没有为调用工具设任何奖励或惩罚。

- **工具没用时，模型会放弃它。** GSM8K 上这个模型的错误主要是推理错而不是算错。训练后计算器的使用率从六成降到一成半，准确率和不给计算器时相同。
- **工具有用时，模型会学会它。** 在数字很大、心算必错的应用题上（`examples/calculation_problems.py`），不给计算器训练后只能做对不到两成；给了计算器，即使提示里没有任何用法示范、模型起初只有百分之五的时候去用，十轮之内使用率就到了百分之百，测试集接近全对。
- **"去用工具"能迁移到没见过的题型，"怎么列式"需要多样的训练题目。** 只用八种题型训练时，换成没见过的题型，模型仍然每道题都用计算器，但只做对四成多：它把训练题型上的解法套到了新题上。把 GSM8K 混进训练之后（`examples/mixed_calculation.py`），同样的新题型能做对七到八成，三个随机种子都是如此。
- **"按需使用"没有稳定出现。** 两类题混合训练时，我们希望模型在计算题上用计算器、在 GSM8K 上不用。计算题上三个种子都是每题都用、接近全对；GSM8K 上的使用率却因种子而异，从两成到七成不等，用得越多的那次 GSM8K 准确率越低，相差约七个百分点。训练过程中模型会先学成"所有题都用"，再慢慢在 GSM8K 上退回去；退回去比冲上去慢得多，训练结束时停在哪里并不确定。在不需要工具的题上多用工具只损失几个百分点，这个信号不足以让模型可靠地学会区分。
- **给调用一点代价能让"按需使用"稳定下来，但有副作用。** 把环境的 `call_cost` 设为 0.02（答对时每次调用扣 0.02 分）之后，三个种子在 GSM8K 上的使用率都降到了百分之六以下，计算题上仍然每题都用、接近全对。代价是模型为了少扣分，把一道题的几步运算压进一次调用里：训练过的题型上照样做对，没见过的题型上准确率从七到八成掉到五成上下，使用率也下降了。按次数收费买到了节制，同时改变了模型用工具的方式。只想让模型决定"用不用"、不想影响"怎么用"时，代价应该按"这一局是否用过"收，而不是按次数收；这种做法我们还没有验证。

混合训练的几条有三个随机种子，其余结果各只有一个种子。效应很大的几条（使用率从百分之五到百分之百）方向上是可靠的，具体数值不是。

### 长时间训练要让学习率降下来

混合训练时，我们用恒定的学习率跑过一次 120 轮：第 80 到 100 轮模型在 GSM8K 上几乎不用计算器，看起来已经学会了区分；到第 120 轮它又变回每道题都用，GSM8K 准确率掉了二十个百分点。某个中间检查点上表现好，不等于训练收敛到了那里。

- 训练轮数多时，把 `learning_rate_schedule` 设为 `"cosine"`，让策略在后期稳定下来，并且统一使用最后一个检查点。
- 不要看着测试集上的评测曲线挑检查点，那样报告出来的成绩偏高。确实需要挑选时，另外准备一份验证集。

## 训练 MoE 模型

混合专家（MoE）结构的模型可以直接训练，训练流程和普通模型相同。目前只在 OLMoE-1B-7B（Instruct 版）上验证过，路由冻结。推荐的做法是 LoRA 只注入注意力层。示例配置是 `configs/arithmetic_olmoe.toml`。

```bash
grpx doctor --config configs/arithmetic_olmoe.toml
grpx train  --config configs/arithmetic_olmoe.toml
```

在两位数加法上训练 30 轮，三个种子的贪心评测成功率都从 0.40 升到 0.975 以上（0.975、0.990、0.990）。把其中一个检查点直接拿去测没训练过的位数：三位数从 0.16 升到 0.43，四位数没有变化（0.03 到 0.04）。也就是学到的东西能迁移一部分，但还不是稳定的多位数加法。

和普通模型相比，有四点要注意：

- **显式指定 LoRA 注入的层，只写注意力层。** 专家层在不同版本的 transformers 里实现不同。旧版本（4.57）里每个专家是单独的线性层，默认的 `"all-linear"` 会命中三千多个模块。新版本（5.22）里专家是打包在一起的参数，把专家层的名字写进 `lora_target_modules` 后可训练参数约 1.9 亿，在 24 GB 的显卡上试更新跑不动。两种情况下都请显式写 `["q_proj", "k_proj", "v_proj", "o_proj"]`，在 OLMoE 上是 64 个模块、约 420 万参数。预检会报告命中的模块数，命中了专家层或路由层时给出警告。
- **显存按总参数算。** MoE 模型每个 token 只用到一部分专家，速度接近小模型，但全部专家都要放进显存。OLMoE 有 69 亿参数，bfloat16 下权重约 13.8 GB，24 GB 的显卡上只能用 bfloat16，并且放不下第二份权重，所以只能用本地后端。卡上没有推理服务时，可以把 `training.memory_fraction` 调到 0.9。
- **bfloat16 下，同一条序列的对数概率会随批的组成变化。** 同一条序列单独成批，和跟更长的序列拼在一起，个别 token 的对数概率能差零点几（我们见过 0.34）；换成 float32，差别在 1e-5 以下，所以这不是掩码或补齐的错误，是半精度的数值误差在 MoE 模型里被放大了。它带来两个后果：换一种小批设置或换一台机器，训练前的贪心评测可能差几道题；采样时和训练时的批组成不同，两边的对数概率也有这个量级的差别。我们用两种小批设置、在两台机器上各训练过三个种子，最终成绩相同（0.611 和 0.619），训练本身能容忍这个误差。做对比实验时，请让各组使用同一台机器和同样的小批设置。
- **学习率不能靠位移指标来定。** 只能用 bfloat16，位移指标在这个精度下测到的是噪声（见"步长指标"）。请直接看采样成功率和评测结果。
- **先用预检确认任务难度。** 模型大不代表任务对它容易。OLMoE 在四位数加法上的起点只有 0.02 左右，两位数才落在适合训练的范围里，所以示例配置用的是两位数（`digits = 2`）。

**路由诊断。** MoE 模型在测步长指标的那些轮会多记录一组 `routing_` 开头的字段：

| 字段 | 含义 |
|---|---|
| `routing_changed_position_fraction_mean`、`routing_changed_position_fraction_maximum` | 更新前后，每层里所选专家发生变化的位置比例（各层平均、各层最大） |
| `routing_replaced_expert_fraction_mean` | 被换掉的专家占每个位置所选专家的比例 |
| `routing_changed_in_any_layer_fraction` | 至少有一层换了专家的位置比例 |
| `routing_load_entropy_mean`、`routing_load_entropy_minimum` | 专家负载的归一化熵，1.0 表示完全均匀，越低越集中 |
| `routing_load_maximum_ratio` | 负载最高的专家是均匀负载的多少倍 |
| `routing_unused_expert_fraction` | 这批数据里一次都没被选中的专家比例。数据量小时本来就不为 0，请看趋势 |

我们在 OLMoE 上看到：同一组权重前向两次，路由完全相同；一次正常的更新（学习率 1e-5）会让约一半的位置至少在一层换专家，但每个位置平均换掉的专家不到 1%。换了专家的 token 步长的尾部更重、被裁剪的比例更高（20% 对 10%，282 个 token），但没换专家的 token 同样有重尾，路由不是主要来源。

训练 30 轮的过程中专家负载没有向少数专家集中：负载的归一化熵一直在 0.86 到 0.88 之间，负载最高的专家始终是均匀负载的 7 倍左右，这个不均匀在训练前就有。也就是路由冻结、只训练注意力层时，我们没有看到 RL 训练让专家负载塌缩。

组内没有信号、没有做更新的轮次不记录这些字段。

**vLLM 上的 MoE 模型。** 把本地后端训练出的适配器加载到 vLLM 0.18 上评测，结果和本地后端一致（不带适配器 0.38，带适配器 0.97；本地后端是 0.40 和 0.975），说明只注入注意力层的 LoRA 在 vLLM 的 MoE 模型上确实生效。不同版本的 vLLM 对 MoE 模型的 LoRA 支持差别很大，换版本后请重新确认。

用 vLLM 后端训练也验证过一次（两位数和三位数混合的加法，60 轮，一个种子，训练端和推理服务在同一张 96 GB 的显卡上）：500 道三位数题上的成绩是 0.612，本地后端同一个种子是 0.618；采样从每轮约 1.7 秒降到 0.2 秒以内。两端对数概率差的中位数全程在千分之一以下，没有逐轮变大。95 分位比普通模型大得多，第 0 轮是 0.44，训练中段个别轮超过 1，到模型的回答变得确定之后降到 0.04。这是上面说的 bfloat16 下批组成的影响，不是同步失效；判断同步是否有效请看中位数。OLMoE 的两份权重在 24 GB 的显卡上放不下，所以这条路需要更大的显存。

### LoRA 放在注意力层还是专家层

我们在两位数和三位数混合的加法上比较过两种做法，每种三个种子，用 500 道三位数的题评测（两位数很快就全对，分不出差别）。专家层的 LoRA 需要约 48 GB 的显存，这组实验是在一张 96 GB 的显卡上做的。

- 同样是秩 16、训练 60 轮，加挂专家层明显更好：0.71 对 0.62。但这时专家层那组的可训练参数是 1.89 亿，只注入注意力层的是 420 万。
- 把注意力层的秩加到 128（3400 万参数），60 轮就到了 0.72，和加挂专家层持平。
- 训练到 150 轮，加挂专家层是 0.80，三个种子很接近；注意力层秩 128 的三个种子是 0.88、0.87 和 0.70，平均 0.81，其中一个种子在第 60 轮之后不再提高，后期还小幅回落。
- 把学习率调大三倍也能补上大部分差距，但种子之间差别很大，不如加秩。

结论：**差距来自可训练参数的多少，不是 LoRA 放在哪。** 效果不够时先加大注意力层的秩。它每轮的耗时约为加挂专家层的三分之一，显存约为一半，24 GB 的显卡能跑，vLLM 也支持。加挂专家层唯一的好处是三个种子的结果更一致，这一点只有三个种子的依据。

这组实验里专家层的设置是：`down_proj` 秩 16，`gate_up_proj` 秩 32，缩放系数都是 2。PEFT 加载这种配置时会警告 `rank_pattern` 没有匹配到模块，实际上是生效了的。

没有验证过的情况：训练路由、专家层的 LoRA 在 vLLM 上是否生效、更大的 MoE 模型。

## 使用 vLLM 后端

本地后端不需要任何额外服务，是默认选择。vLLM 后端把采样交给独立的推理服务，训练端每轮更新后把 LoRA 权重同步过去。模型越大、回答越长，它的优势越明显；模型很小、回答很短时，每轮的时间主要花在训练端的更新上，换后端带来的提速有限。

vLLM 只支持 Linux。在 Windows 上需要通过 WSL2 运行，建议训练端也放在 WSL2 里，这样两边看到的路径一致。

### 启动推理服务

推理服务和训练端建议各用一个独立的 Python 环境，避免依赖版本互相覆盖。

```bash
export VLLM_ALLOW_RUNTIME_LORA_UPDATING=1
vllm serve Qwen/Qwen2.5-0.5B-Instruct \
    --enable-lora --max-lora-rank 16 \
    --generation-config vllm \
    --gpu-memory-utilization 0.15 \
    --max-model-len 2048 \
    --port 8000
```

- `VLLM_ALLOW_RUNTIME_LORA_UPDATING`：允许运行时加载适配器。没有它，同步接口会返回 404。
- `--generation-config vllm`：不套用模型自带的生成配置，保证采样分布就是策略本身。
- `--max-lora-rank`：不能小于配置里的 `lora_rank`。
- `--gpu-memory-utilization`：服务预占的显存比例。和训练端共用一张显卡时要调小，见下面的说明。

### 配置

```toml
[backend]
type = "vllm"
base_url = "http://localhost:8000"
max_new_tokens = 32
temperature = 1.0
max_concurrent_requests = 64
```

`[model]` 里的模型必须和推理服务加载的是同一个。这一点会被检查三次，任何一次不通过都会直接中止：

- 启动时，比对推理服务的基座模型和 `[model].name`。
- 每次同步后，核对适配器记录的基座和推理服务上的基座是否一致。
- 第 0 轮采样后，比较两边对同一批 token 给出的对数概率，中位数相差超过 0.05 就中止。

需要这些检查，是因为 vLLM 在适配器和基座形状不匹配时不会报错：加载接口返回成功，之后的采样实际用的是没有适配器的基座。不检查的话，训练会照常跑完，日志里的成功率和回报却来自另一个模型。

然后照常运行。预检会额外检查服务是否可达、权重同步是否真的生效。

```bash
grpx doctor --config my_task.toml
grpx train --config my_task.toml
```

### 单卡上同时运行服务和训练

两个进程共用一张显卡时，显存要留出余量：

- **先启动服务，再启动训练。**
- 把 `--gpu-memory-utilization` 调小。0.5B 的模型用 0.15 就足够。
- 训练端会把自己可用的显存限制在整张卡的 60%（`training.memory_fraction`），并在日志里同时记录实际使用和实际占住的显存峰值。

在 Windows 和 WSL2 上要特别注意：**显存不够时不一定报错，而是把超出的部分放进系统内存，表现为训练慢一到两个数量级**。典型特征是 `nvidia-smi` 里显存占满、利用率 100%、功耗却很低。遇到训练突然变得很慢，先看显存。

### 使用多张显卡

训练端只使用一张显卡。有多张卡时，可以把推理服务放到别的卡上，两边不再争用显存：

```bash
CUDA_VISIBLE_DEVICES=1 vllm serve ...      # 推理服务用第二张卡，其余参数不变
```

```toml
[training]
device = "cuda:0"
memory_fraction = 0.95      # 独占一张卡，不必再留余量
```

采样是瓶颈时，可以启动多个推理服务，把地址写成列表：

```toml
[backend]
base_url = ["http://localhost:8000", "http://localhost:8001"]
```

- 每条轨迹固定发往一个服务，同一条对话的后续请求可以复用那个服务上的缓存。
- 每次同步会把权重加载到所有服务上，全部成功才算成功；任何一个失败，这次同步整体撤回并中止训练，不会出现各服务权重版本不一致的情况。
- 模型一致性检查对每个服务各做一遍。日志里的 `backend_log_probability_gap_` 两项取各服务中最大的，`backend_log_probability_gap_worst_url` 标出是哪一个。

多个推理服务的用法在单卡上用两个服务验证过；推理和训练分卡、多卡之间的实际耗时还没有测过。

### 确认同步有效

接口返回成功，不代表推理服务已经用上了新权重。日志里的 `backend_log_probability_gap_median` 和 `backend_log_probability_gap_p95` 是为此准备的：对同一批采到的 token，比较推理服务给出的对数概率和训练端自己算出的值。

- 正常情况下只有精度带来的微小差别，中位数在千分之几的量级。
- 中位数逐轮明显变大，说明推理服务没有跟上训练端的权重，训练结果不可信。
- 第 0 轮的中位数就很大（正常是千分之几），说明训练端和推理服务加载的不是同一个模型。超过 0.05 时训练会直接中止。最常见的原因是推理服务还挂着上一个实验的模型。
- 训练端用 float32 时，95 分位会在训练开头的几轮里逐渐升高，中位数保持不变。这是两边精度不同、差别随 LoRA 权重增大而拉开造成的，不是同步失效。训练端改用 bfloat16 后，95 分位基本持平。

### vLLM 后端的限制

- 只支持 LoRA 模型。
- 推理服务只能用半精度。训练端默认用 float32，两边的数值有微小差别；把 `model.dtype` 设为 `"bfloat16"` 可以缩小这个差别。
- 推理服务需要手动启动和关闭。
- 采样和训练是严格交替的，没有异步。

每次同步都会用一个新的名字加载适配器（`policy-<运行名>-<版本号>`），并卸载上一个版本。训练结束后，最后一个版本会留在服务上，方便事后检查；需要腾出显存时手动卸载，或者重启服务。

## 预检：`grpx doctor`

预检由便宜到贵分阶段进行，前面的阶段失败就不再加载模型。每一项给出"通过 / 警告 / 失败"和一句建议，有失败项时退出码为 1。

| 类别 | 检查项 | 触发条件 | 意味着什么 |
|---|---|---|---|
| 环境 | CUDA、依赖版本 | 看不到 CUDA，或依赖版本过低 | 环境本身不满足运行条件 |
| 任务 | 训练集、评测集 | 不是列表，或题目数少于每轮要抽的组数 | 数据集函数的返回值不对，或数据量不够 |
| 任务 | 环境试运行 | `reset`、`step` 的返回值形状不对，或抛出异常 | 环境接口有误，或处理不了任意文本 |
| 模型 | LoRA 注入的层 | 一个模块都没命中：失败；命中了 MoE 的专家层或路由层：警告 | 模块名写错了；或者注入的范围比预想的大得多，同时报告命中的模块数，以及命中的专家模块的参数量 |
| 模型 | 对话模板 | 分词器没有对话模板 | 这个模型不是对话模型，或者需要手动设置模板 |
| 采样 | 成功率 | 恰好为 0，或高于 0.9 | 起点过低，或任务太容易、没有可学的空间 |
| 采样 | 有信号的比例 | 低于 0.25 | 多数组内回报完全相同，考虑分级回报或增大 `group_size` |
| 采样 | 结束原因 | 截断比例高于 0.2 | 增大 `max_new_tokens`，或在提示词里限制输出格式 |
| 采样 | 回答长度 | 95 分位达到生成上限的 90% | 同上 |
| 采样 | 截断却高回报 | 存在被截断、而回报函数或环境给了 0.5 以上回报的回答 | 回报函数看不到截断。确认 `truncated_reward` 没有被设成 `null` |
| 采样 | 截断占便宜 | 正常结束的轨迹里，有整局回报低于 `truncated_reward` 的 | 被截断比这部分正常结局得分更高，模型可能学着把回答写到截断。调低 `truncated_reward` |
| 采样 | 生成结束 | 配置了停止串却一次都没有触发 | 停止串多半写错了。同时报告以结束 token、停止串、长度上限结束的比例 |
| 采样 | 步级信号覆盖率 | 低于 0.05（仅在启用步级优势时报告） | 步级分组没有生效，当前配置等同于 GRPO |
| 训推一致 | 回答 token 的对数概率 | 对数概率低于 -15 的 token 占比超过 0.005，或平均值低于 -3 | 训练端认为采到的 token 几乎不可能：采样和训练看到的上下文不一致 |
| 训推一致 | 首步 ratio | 偏离 1 超过 1e-3 | 参数尚未更新时 ratio 应恰好为 1；不为 1 通常是模型里有 dropout |
| 采样 | 超长行丢弃比例 | 单独一行就超过 `max_tokens_per_minibatch`、因而不参与更新的行，超过 5% 警告，超过 20% 失败 | 调大 `max_tokens_per_minibatch`，或在环境里限制一局的总长度 |
| 试更新 | 最坏小批 | 峰值超过训练端的显存上限，或摸底时显存不足：失败；超过上限的 80%：警告 | 按当前的小批预算构造最吃显存的小批（补齐后总长度最大的，和回答位置最多的），实际前向和反向一次，给出显存峰值。它是训练中单个小批显存的上界 |
| 试更新 | 位移 | 裁剪比例高于 0.2 或 95 分位高于 1.0；95 分位低于 0.01 | 学习率过大；学习率过小 |
| 试更新 | 显存 | 同上，按训练端的显存上限判定 | 余量不足，减小 `max_tokens_per_minibatch` |
| 试更新 | 预计耗时 | 不判定，只报告 | 每轮耗时和总耗时的估计 |

预检采样用的种子和题目与正式训练的第 0 轮相同，看到的就是训练开头会遇到的情况。

预检和训练使用同一个显存上限（`training.memory_fraction`，默认是整张卡的 60%），预检通过的配置在训练时不会因为上限不同而显存不足。接近上限时，实际训练仍可能因为显存碎片而失败，这时设置环境变量 `PYTORCH_CUDA_ALLOC_CONF=expandable_segments:True`，或调小 `max_tokens_per_minibatch`。

试更新用的是不带预热的满学习率，比真实训练的第一步更激进，所以位移一项的阈值比"怎么读训练日志"一节里的参考范围宽。试更新之后模型权重会还原。

`model.dtype` 为 `"bfloat16"` 时，位移一项不再判定学习率过大或过小，只在裁剪比例过高时警告，原因见"步长指标"里关于混合精度的说明。

## 怎么读训练日志

每一轮在终端打印一行摘要，完整数值写入 `metrics.jsonl`。

### 采样指标

| 字段 | 含义 |
|---|---|
| `mean_reward` | 本轮采样的平均回报 |
| `success_fraction` | 本轮采样的成功率 |
| `signal_fraction` | 有组内差异、参与了训练的轨迹占比 |
| `length_limit_fraction` | 被生成长度截断的轨迹占比 |
| `step_limit_fraction` | 用尽步数仍未结束的轨迹占比 |
| `mean_step_count` | 平均每条轨迹走了几步 |
| `step_signal_coverage` | 能拿到步级优势的步数占比。是否启用 GiGPO 都会统计，未启用时表示"如果启用，会有多少步受影响" |
| `environment_<名字>` | 环境的 `metrics()` 返回的自定义指标，在所有轨迹上取平均 |
| `backend_log_probability_gap_median`、`backend_log_probability_gap_p95` | 仅 vLLM 后端。推理服务与训练端对同一批 token 给出的对数概率之差，见"使用 vLLM 后端"一节 |

这些指标是在本轮更新**之前**、用本轮新抽的题目采样得到的。每轮题目数量有限，单轮的波动较大，建议看若干轮的滑动平均。

### 评测指标

以 `evaluation_` 开头，在固定的评测集上用贪心解码得到，不同轮次之间可以直接比较。判断训练是否有效，以评测指标为准。

### 步长指标

以 `shift_` 开头。更新之后额外做一次前向，测量策略在本轮数据上实际变化了多少。默认每轮都测；`shift_measurement_interval` 大于 1 时只在部分轮次测量，其余轮次的日志里没有这三个字段。这次前向的耗时单独记在 `shift_seconds` 里，不计入 `update_seconds`。

| 字段 | 含义 | 参考范围 |
|---|---|---|
| `shift_clip_fraction` | 概率变化超过裁剪范围的 token 占比 | 低于 0.1 |
| `shift_percentile_95_absolute_log_ratio` | 对数概率变化的 95 分位 | 低于 0.5 |
| `shift_median_absolute_log_ratio` | 对数概率变化的中位数 | 仅供参考 |

每轮只更新一次时，PPO 的裁剪不起作用，步长完全由学习率和预热决定。这三个指标是判断学习率是否合适的依据：长期超出参考范围就降低学习率，远低于参考范围可以提高。

中位数主要反映策略有多确定，训练后期降到很小是正常现象，不代表步长过小。回答里大多数 token 几乎确定的任务（比如 GSM8K）上，中位数会降到 float32 的舍入误差量级，这时请看 95 分位和裁剪比例。

使用混合精度时，这三个指标有一个与学习率无关的底噪。bfloat16 的前向对权重的任何变化都很敏感：哪怕 LoRA 参数只动了 1e-8，舍入结果也会不同，读数就落在底噪的量级上；权重完全不变时读数为 0。在 token 普遍不确定的任务上，底噪和正常学习率下的真实位移一样大（猜数字上中位数是千分之几，95 分位接近 0.1），此时这三个指标不能用来判断学习率。回答里大多数 token 几乎确定的任务上，底噪小得多。

需要判断学习率是否合适时，用 float32 跑一次预检，定下学习率之后再切到混合精度训练。混合精度下这三个指标参考价值有限，可以把 `shift_measurement_interval` 调大或设为 0，省下这次前向。

### 耗时和显存

| 字段 | 含义 |
|---|---|
| `oversized_row_count`、`oversized_row_max_length` | 这一轮有多少行因为超过 `max_tokens_per_minibatch` 而没有参与更新，以及其中最长的一行有多少个 token。平时应为 0 |
| `evaluation_seconds`、`sampling_seconds`、`metrics_seconds`、`update_seconds`、`shift_seconds`、`synchronize_seconds` | 这一轮各阶段的耗时 |
| `iteration_seconds` | 这一轮的总耗时 |
| `peak_memory_gigabytes` | 这一轮训练进程实际使用的显存峰值 |
| `peak_reserved_memory_gigabytes` | 这一轮训练进程实际占住的显存峰值，包括已释放但尚未归还的部分 |

某一轮突然变慢时，先看是哪个阶段变慢，再看两个显存峰值。占住的量远大于实际使用的量，通常意味着有不带梯度的计算没有放在 `torch.no_grad()` 里。

### 常见现象

| 现象 | 可能的原因 | 处理 |
|---|---|---|
| 回报不涨，`signal_fraction` 很低 | 回报函数没有区分度 | 改用分级回报，或增大 `group_size` |
| 回报涨到一定程度后停住，`signal_fraction` 逐渐降低 | 剩下的题目上模型每次给出相同的回答，没有差异可学 | 提高采样温度，或接受这个上限 |
| `length_limit_fraction` 很高 | 模型回答太长 | 增大 `max_new_tokens`，或在提示词里限制格式 |
| `length_limit_fraction` 在训练中途突然升高 | 模型学会了给出答案后不停笔，或陷入重复 | 抽几条被截断的回答看原文；检查回报函数有没有"多写也能得分"的路径 |
| 回答逐渐变长，但准确率和截断率正常 | 回报里没有对长度的约束，长度会自由漂移。我们在 GSM8K 上约一半的运行里见过，与算法无关，也不带来更高的准确率 | 在意推理成本时，在回报里加一项对长度的轻微惩罚 |
| `shift_clip_fraction` 持续偏高 | 学习率过大 | 降低 `learning_rate` |
| `loss` 接近 0 或不随训练下降 | 正常 | 见下面的说明 |

关于 `loss`：每轮只更新一次时，日志里的 `loss` 是更新之前计算的，此时新旧策略相同，它的数值只取决于优势的加权平均，不反映训练进展。单轮任务里它恒接近 0。请不要用它判断训练是否有效。

### 对比实验的注意事项

- 固定随机种子不保证逐位可复现：GPU 上的部分运算不是确定性的，微小差异会被后续更新放大。
- 比较两个配置时，每个配置至少运行三个种子，看均值和范围。单次运行的差异不能作为结论。
- 训练刚开始的几轮里，不同配置的贪心评测结果可能完全相同，这是因为模型之间的差别还不足以改变贪心解码的输出，不是程序错误。
- 反过来，训练刚开始时贪心评测只会落在少数几个数值上，同一配置重复运行也可能落在不同的数值上。只训练几轮的评测结果相同，不能证明两次训练等价；结果不同，也不能证明训练有差别。要验证一处改动不影响训练，请固定同一批轨迹，直接比较更新前后的 `shift_` 指标。

## 已知的局限

- 训练只使用一张显卡。推理服务可以放在别的显卡上，也可以启动多个。
- vLLM 后端只支持 LoRA，采样和训练严格交替，尚无异步采样。
- 只支持 LoRA 微调。
- 多轮任务里，默认每一步都会把完整的对话历史重新前向一次，对话很长时显存和耗时增长较快。只追加的对话可以用 `merge_append_only_turns` 合并，其他情况没有优化。
- 混合精度只在 Qwen2.5 的两个模型和 OLMoE-1B-7B 上验证过。
- 完整的实验只在 Qwen2.5-0.5B 和 Qwen2.5-1.5B 上做过。任务是四位数加法、猜数字、冰湖寻路、GSM8K，以及带计算器的 GSM8K 和计算应用题。
- MoE 模型的专家层 LoRA 在 24 GB 的显卡上跑不动（需要约 48 GB），路由的训练没有实现。
- MoE 模型只在 OLMoE-1B-7B 上验证过，任务是两位数和三位数的加法。本地后端每个设置三个种子，vLLM 后端只训练过一个种子。
- 单独一行就超过 `max_tokens_per_minibatch` 的轨迹不参与更新。这类轨迹通常是写得特别长的失败回答，跳过它们意味着模型不会因为写得太长而受到惩罚。日志里的 `oversized_row_count` 记录每轮跳过了多少行，比例超过 5% 时训练会给出提示，这时应调大预算，或在环境里限制一局的总长度。
